# Конечные метаградиенты через clipping в JAX

Jabrail Khalil · 12 октября 2026

Нулевой градиент внутренней задачи не обязательно означает нулевой градиент внешней. В этом разборе я воспроизвожу случай, когда ограничение нормы сохраняет правильный результат прямого прохода, но превращает обратную производную в NaN. Я сравниваю результат с аналитическим ответом и независимыми конечными разностями, затем проверяю исправление в обычном режиме, под `jit` и под `vmap`.

Ошибка зарегистрирована в [Optax #1814](https://github.com/google-deepmind/optax/issues/1814), исправление предложено в [PR #1815](https://github.com/google-deepmind/optax/pull/1815). На дату публикации PR открыт; это не заявление о включении исправления в релиз.

Исходное поведение проверено на [Optax main в revision 8589d97](https://github.com/google-deepmind/optax/blob/8589d974e565fbf1bfa1cdf8d94f5ecdf8ebe93c/optax/transforms/_clipping.py), предложенная реализация закреплена в [revision 5a39453](https://github.com/google-deepmind/optax/blob/5a39453983cc19f3c16f5ad9490868bce35e3c55/optax/transforms/_clipping.py). Учебный скрипт ниже сохраняет обе формулы явно и не зависит от будущего состояния main.

## Почему в нуле нужна единичная производная

Для положительного порога `c` global-norm clipping возвращает `x`, если `||x|| < c`, и `c * x / ||x||` иначе. В окрестности нуля отображение тождественное. Следовательно, его якобиан в нуле должен быть единичной матрицей.

Векторное сокращение исходного выражения для порога 1 выглядит так:

```python
norm = jnp.sqrt(jnp.vdot(x, x).real)
return jax.lax.select(norm < 1.0, x, x / norm)
```

При `x = 0` прямой результат равен нулю, а `jax.jacfwd` возвращает единичную матрицу. Но `jax.jacrev` выдаёт NaN. Неиспользуемая ветка содержит деление на ноль и производную корня в нуле. При обратном проходе нулевая сопряжённая величина не делает неопределённую арифметику безопасной: `0 * NaN` остаётся NaN. Демон здесь маленький, но умеет прятаться в правильном прямом ответе.

## Независимый ответ для внутреннего обучения

Возьмём внутреннюю функцию потерь `L(p) = sum(p**2) / 2` и три шага с learning rate 0.1. При малых `p` clipping не активен, градиент внутренней функции равен `p`, поэтому после трёх шагов:

```text
p3 = 0.9**3 * p0
outer_loss = sum((p3 - 1)**2)
d outer_loss / d p0 при p0 = 0: -2 * 0.9**3 = -1.458
```

Здесь внутренний градиент в нуле равен нулю, но внешний градиент по начальным параметрам — нет. Исходный clipping даёт NaN вместо `-1.458` в каждом компоненте. Это воспроизводимый пример дифференцирования через оптимизацию, а не измерение качества обученной модели.

Я отдельно вычисляю внешний loss в NumPy float64, без JAX и автоматического дифференцирования. Центральные конечные разности с шагом `1e-5` дают примерно `-1.4580000000208313`. Эта проверка не зависит от того же правила autodiff, которое мы проверяем.

## Маска должна стоять до корня

Смена `<` на `<=` не исправляет обратную производную при положительном пороге: в нуле обе проверки истинны. Маска только вокруг уже вычисленного `norm` также оставляет проблемную производную корня. Обе неудачные попытки включены в исполняемый пример как отрицательные контроли.

Исправленное векторное выражение:

```python
norm_squared = jnp.vdot(x, x).real
trigger = jnp.sqrt(norm_squared) < 1.0
denominator = jnp.sqrt(jnp.where(trigger, 1.0, norm_squared))
return jax.lax.select(trigger, x, x / denominator)
```

Корень в условии определяет булев выбор; через само сравнение производная не распространяется. Для неиспользуемой ветки деления мы подставляем безопасный аргумент **до** корня. При активном clipping знаменатель остаётся исходной нормой. Строгое сравнение порога сохранено; epsilon и новые допуски не вводятся.

Это частный случай правила из [официального JAX FAQ](https://docs.jax.dev/en/latest/faq.html#gradients-contain-nan-where-using-where): для конечной обратной производной безопасное значение нужно подставлять внутри операции с неопределённой производной, а не только выбирать её результат снаружи.

Это отдельная задача от [Optax #1752](https://github.com/google-deepmind/optax/pull/1752), где обсуждается прямой результат при нулевых норме и пороге. В учебном примере порог фиксирован и положителен. Пример работает с одним вещественным вектором и не заменяет публичный API Optax для деревьев параметров.

## Запуск и проверенные результаты

Из корня репозитория создайте отдельное окружение Python 3.12 и активируйте его:

```sh
python -m venv .venv-clipping
# Linux / macOS
source .venv-clipping/bin/activate
python -m pip install -r requirements-clipping.txt
python examples/clipping_meta_gradients.py
```

В PowerShell вместо `source` используйте `.\.venv-clipping\Scripts\Activate.ps1`. Другие лабораторные работы репозитория используют свои окружения и source revisions; смешивать их зависимости не нужно.

Скрипт завершается ошибкой при неожиданном результате. Он проверяет NaN в исходной обратной производной, единичный исправленный якобиан, аналитический метаградиент, отдельный NumPy-расчёт и производные ненулевых векторов ниже и выше порога. Обычный и JIT-режимы проверяются отдельно; `vmap` проверяет батч якобианов в нуле.

Локальные проверки прошли на Windows CPU с Python 3.12.10, JAX/jaxlib 0.11.2 и 0.5.3, NumPy 2.5.4. Исправленный float32 метаградиент равен `-1.4579999446868896`. [Выводы запусков](../validation/clipping/) содержат версии и результаты; отдельная задача GitHub Actions запускает этот пример с закреплёнными зависимостями.

В самом Optax до изменения реализации новые проверки обратного якобиана и метаградиента падали в обычном и JIT-режимах. После исправления выбранный расширенный набор дал 789 пройденных тестов, 62 пропуска и 724 пройденных подслучая. Это выбранные проверки transforms, numerics, tree math и optimizer aliases, а не вся upstream-матрица. Состояние upstream CI следует смотреть непосредственно в PR.

## Упражнение для самостоятельной проверки

Верните в `fixed_clip` маску после корня и запустите скрипт. Проверка единичного обратного якобиана должна упасть. Затем замените внешний target 1 на 2 и независимо выведите новый ответ `-4 * 0.9**3`; обновлять ожидание без этого вывода не нужно. Наконец, сравните ненулевой clipped-якобиан с формулой `I / ||x|| - x xᵀ / ||x||**3` для порога 1, отдельно от точки переключения.

Главный практический вывод: правильный прямой ответ не гарантирует правильную производную. Для дифференцируемого оптимизатора стоит проверять нулевые обновления, производную неактивной ветки и независимый ответ для короткого внутреннего цикла.

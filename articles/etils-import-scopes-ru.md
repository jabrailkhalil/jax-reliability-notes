# Изоляция lazy imports и очистка ресурсов в etils

Jabrail Khalil · 12 октября 2026

`with epy.lazy_imports()` откладывает загрузку модулей до первого обращения к ним. Но замена `builtins.__import__` действует на весь процесс, а не только на написанный рядом блок. Если в этот момент другой поток или сборщик мусора выполняет обычный импорт, он может получить lazy proxy вместо настоящего объекта. Для финализатора системного семафора это превращается в утечку ресурса.

Исходные воспроизведения и направление исправления предложил mahdi-shafiei в [etils #838](https://github.com/google/etils/issues/838). Я воспроизвёл ошибки, добавил проверки и подготовил [PR #839](https://github.com/google/etils/pull/839). На дату публикации PR открыт и ожидает review. Ниже — самостоятельная лабораторная работа на закреплённых версиях, а не объявление о релизе или проведённом занятии.

## Почему чужой импорт становится ленивым

Обычный импорт `from json import dumps` возвращает функцию. Исходный hook перехватывает его без проверки вызывающего и возвращает `LazyModule`. Проверка имени импортируемого модуля здесь не помогает: `json` одинаков и для намеренно отложенного импорта, и для чужого рабочего потока.

Проверять только `globals` тоже недостаточно. Функция, вызванная из блока, может иметь те же module globals, но её импорт не является непосредственным импортом этого блока. В предложенном исправлении dispatcher сопоставляет вызывающий frame и идентификатор потока с активными контекстами. Чужой вызов идёт в сохранённый импортёр.

| Где выполняется импорт | Требуемое поведение |
| --- | --- |
| Непосредственно в активном lazy-блоке | Создать lazy proxy |
| В обычной вызываемой функции или другом потоке | Выполнить обычный импорт |
| В GC-финализаторе | Выполнить обычный импорт, включая относительный |
| В оставшемся активном контексте после выхода другого потока | Сохранить его lazy-поведение |

`with` сам по себе не создаёт новую область видимости Python. Нужная граница перехвата — часть реализации hook, а не свойство синтаксиса.

## Как импорт ломает освобождение семафора

Финализатор `multiprocessing.synchronize.SemLock` импортирует `unregister` из соседнего `resource_tracker`. В исходной реализации этот относительный импорт попадает в lazy-hook, который запрещает относительные импорты. Финализатор выбрасывает `ValueError`, а имя семафора остаётся в `/dev/shm`.

Для воспроизведения я создаю четыре настоящих named semaphores в циклических объектах, отключаю автоматический GC, затем явно вызываю `gc.collect()` внутри lazy-блока. Это задаёт момент финализации без надежды на случайное выделение памяти. На Linux база оставляет четыре имени, исправление — ни одного. Сам probe удаляет только собственные оставшиеся имена, поэтому отрицательный контроль не оставляет мусор в системе.

Это другой дефект, чем последовательное завершение workers из [Grain shutdown lab](grain-shutdown-ru.md). Оба относятся к lifecycle ML-инфраструктуры, но ускорение `close()` само по себе не исправляет чужой глобальный import-hook.

## Почему обычного try finally недостаточно

Исходный контекст сохраняет текущий импортёр при входе и возвращает его при выходе. Такой стек работает для вложенности: A входит, B входит, B выходит, A выходит. Для потоков допустим другой порядок: A входит, B входит, A выходит, B выходит. Тогда A может отключить ещё нужный B hook, а B в конце вернуть уже устаревший hook A.

Предложенный вариант устанавливает один dispatcher и ведёт общий реестр активных контекстов. Выход удаляет конкретный контекст, а исходный импортёр восстанавливается только после удаления последнего. Короткая блокировка защищает реестр; выполнять импорт и callbacks под этой блокировкой не нужно.

Совместимость требует больше проверки, чем простое сравнение одного frame: `lazy_api_imports`, делегирующий context manager, ExitStack и ContextDecorator входят в контекст через вспомогательные frames. В upstream-тестах эти формы, вложенные callbacks, прежний пользовательский hook и освобождение сохранённых frames проверяются отдельно. Демон здесь не `finally`: демон — предположение, что все потоки выходят из блоков как аккуратная матрёшка.

## Воспроизводимый запуск

Нужны Python 3.11 или новее и Git. Из корня этого репозитория создайте отдельное окружение:

```sh
python -m venv .lab/etils-env
```

Активируйте его через `source .lab/etils-env/bin/activate` в Linux/macOS или `.\.lab\etils-env\Scripts\Activate.ps1` в PowerShell. Затем выполните:

```sh
git -c core.autocrlf=false clone --filter=blob:none https://github.com/google/etils.git .lab/etils
git -C .lab/etils -c core.autocrlf=false checkout d18f006162a8da2b7eb79de2e1e1cac0d07774c5
python -m pip install ".lab/etils[epy]"
python examples/etils_import_scopes.py --expect baseline

git -C .lab/etils fetch https://github.com/jabrailkhalil/etils.git 7875132c8a7567ad71035704081d1c9a210353fc
git -C .lab/etils -c core.autocrlf=false checkout 7875132c8a7567ad71035704081d1c9a210353fc
python -m pip install --force-reinstall --no-deps .lab/etils
python examples/etils_import_scopes.py --expect fixed
```

Скрипт использует настоящий установленный пакет, проверяет SHA-256 исходного модуля и не подменяет его учебной реализацией. `core.autocrlf=false` сохраняет проверяемые байты в Windows. Установка исполняет доверенный код выбранных revision, как обычная установка пакета.

На macOS/Windows `baseline` требует ровно шесть конкретных ошибочных наблюдений и три успешных контроля; `fixed` — девять успешных наблюдений. Linux добавляет настоящий semaphore probe: семь ожидаемых ошибок на базе и десять успешных наблюдений с исправлением. Traceback финализатора в Linux baseline — воспроизводимая ошибка исходного кода; любой другой неожиданный результат завершает lab ненулевым кодом. Linux-проверка ресурсов не объявляется выполненной на остальных платформах.

## Проверки самого исправления

Лабораторная работа показывает механизм, а не заменяет тесты проекта. [Матрица head и base](https://github.com/jabrailkhalil/etils/actions/runs/38295186870) проверила Linux Python 3.11/3.12, macOS 3.13 и Windows 3.14: весь `epy` даёт 64 passed без skips с исправлением и точно 10 failures плюс 54 passing controls на базе. Каждый head также проходит 200 управляемых пар перекрывающихся контекстов; тесты обнаруживают две намеренные поломки — перехват чужого scope и слишком раннее восстановление hook.

[Полный неизменённый workflow проекта в моём fork](https://github.com/jabrailkhalil/etils/actions/runs/38295907134) с `.[all,dev]` прошёл на Linux Python 3.11 и 3.12: по 697 passed, 4 skipped, 2 xfailed и 392 успешных subtests. Проверки выполняются на CPU; это не запуск обучения или ускорителей. Существующие предупреждения TFDS при очистке fixtures одинаково воспроизводятся на базе и head и не выдаются за исправленные этим PR.

## Упражнения

Нарисуйте порядок A enter, B enter, A exit, B exit и выпишите, какой импортёр должен работать после каждого шага. Затем замените порядок выхода на LIFO: этот контроль должен проходить и до исправления.

Добавьте функцию с обычным импортом в тот же Python-модуль, где открыт lazy-блок. Проверка должна различать её frame и frame самого блока, даже при одинаковых `globals`. Наконец, придумайте отрицательный контроль для реестра: удаление одного scope не должно отключать оставшийся. Практический результат — проверять границы глобального hook и владение ресурсами, а не только успешный импорт нужного пакета.

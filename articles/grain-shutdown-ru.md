# Проверка параллельного завершения workers в Google Grain

Jabrail Khalil · 12 октября 2026

Закрытие pipeline тоже часть его корректности. Я разбираю [Grain #1410](https://github.com/google/grain/issues/1410): последовательное закрытие дочерних итераторов складывает задержки завершения независимых workers. В [моём PR #1430](https://github.com/google/grain/pull/1430) cleanup запускается параллельно, но `close()` по-прежнему ждёт его окончания. Ни worker timeout, ни тестовые пороги не ослабляются.

На дату публикации PR открыт и ожидает review; upstream Build & Test требует разрешения maintainer. Это самостоятельная лабораторная работа, не проведённое занятие и не объявление о релизе Grain.

## Что именно можно ускорить

Если `close()` одного ребёнка ждёт завершения процесса, последовательный цикл приближённо занимает сумму задержек. Для независимых cleanup-операций параллельный запуск позволяет приблизиться к максимальной задержке плюс накладные расходы. Это не ускорение Python-вычислений потоками и не гарантия для детей, разделяющих блокировки или другие ресурсы.

Для конкретного interleave-протокола порядок остаётся таким: остановить prefetch итераторов, начать закрытие активных детей, дождаться каждого начатого cleanup, затем вернуть управление или передать исключение вызывающему. В обычном многодочернем пути ошибка одного ребёнка не должна оставлять остальных незакрытыми. Пустой и однодочерний пути остаются синхронными.

## Проверка протокола вместо гонки секундомера

Проверка вида «закрой восемь workers быстрее X секунд» зависит от загрузки CI. Для основной регрессии я использую `threading.Barrier`: каждый ребёнок входит в `close()` и ждёт остальных. Последовательный алгоритм не может пропустить даже первого участника через барьер; параллельный может. Пятисекундный timeout здесь ограничивает зависание теста, а не задаёт допустимую производительность.

Вторая независимая проверка проще: первый ребёнок выбрасывает заданное исключение, второй считает вызовы `close()`. После завершения многодочернего cleanup счётчики должны быть `[1, 1]`, а вызывающий должен получить тот же объект исключения. Исходный алгоритм оставляет `[1, 0]`. Повторный `close()` не должен закрывать детей снова.

В [исполняемом скрипте](../examples/grain_shutdown.py) три размера барьера — 2, 4 и 8 — и два типа исключений дают пять отрицательных контролей. Ещё семь случаев проверяют пустые и частично заполненные слоты, недоступность новых потоков, финализацию и реальное завершение subprocess. Режим `baseline` успешен только при точном наборе из пяти ожидаемых сбоев и семи успешных контролей. Режим `fixed` требует всех 12 успешных результатов. Неожиданный сбой не превращается в разрешённый `xfail`.

## Почему atexit недостаточно

Первый вариант параллельного cleanup добавил собственную регрессию: Linux CI на Python 3.11 завис в `Thread.start()` при финальной сборке мусора. Это была ошибка исправления, а не повод перезапустить job до зелёного результата. Изолированное воспроизведение на CPython 3.11.17 также зависло; финальный вариант с синхронным путём при `sys.is_finalizing()` завершился нормально.

Вызов из `atexit` и финальный сборщик мусора — разные фазы. Тест удерживает циклический объект до конца интерпретатора и требует реальный маркер `FINAL_GC=True`; обычный shutdown-callback отдельно требует `False`. Подмена `sys.is_finalizing()` полезна для проверки ветки, но не заменяет этот subprocess-тест. [Документация Python](https://docs.python.org/3.11/library/sys.html#sys.is_finalizing) определяет сам индикатор; конкретное зависание установлено воспроизведением, а не универсальным обещанием поведения всех версий Python.

Если создание потока недоступно в обычном cleanup, соответствующий ребёнок закрывается синхронно. Уже запущенные cleanup-потоки всё равно нужно дождаться. Финализация — плохой момент знакомиться с новым потоком: демон уже выключает свет.

## Запуск без нативной сборки Grain

Нужны Python 3.11 или новее и Git. Из корня этого репозитория выполните:

```sh
git init .lab/grain
git -C .lab/grain fetch --depth=1 https://github.com/google/grain.git 7e36b7231574d0f9ab106f903a8d832f58157594
git -C .lab/grain fetch --depth=1 https://github.com/jabrailkhalil/grain.git b24133c928899e86b649d624bea32c3e494483e4
python examples/grain_shutdown.py --source .lab/grain --expect baseline
python examples/grain_shutdown.py --source .lab/grain --expect fixed
```

Команды одинаковы для shell и PowerShell; устанавливать Python-пакеты для этой работы не нужно. Скрипт читает Git blob конкретной revision, проверяет SHA-256 и извлекает AST настоящего `InterleaveDatasetIterator.close()`. Тело метода не переписано в «похожую» учебную реализацию. Проверяется blob, а не рабочая копия, поэтому преобразование LF/CRLF в Windows не меняет проверку источника.

Как и импорт пакета, исполнение извлечённого метода требует доверия к исходникам. Скрипт принимает только две указанные revision с закреплёнными хешами. Fixtures изолируют протокол закрытия; они не воспроизводят процессы Grain, загрузку данных или восстановление checkpoints. Для интеграции нужны отдельные тесты самого проекта.

Локально оба режима прошли на Windows с CPython 3.11.17 и 3.12.10; [JSON-выводы](../validation/grain-shutdown/) содержат каждый результат и хеш источника. [Отдельная задача CI](../.github/workflows/reproduce.yml) запускает эту лабораторную работу на Linux, macOS и Windows с Python 3.11–3.14.

## Измерение с настоящими процессами

Отдельно от учебных fixtures я измерил время `close()` реальных `mp_prefetch` workers на Windows с CPython 3.12.10. В каждый процесс добавлена задержка `atexit` 300 мс, из pipeline получены скалярные данные и PID каждого worker. Ниже медианы трёх повторов на конфигурацию:

| Workers | Исходная база | Предложенное исправление |
| --- | ---: | ---: |
| 2 | 0.897 с | 0.452 с |
| 4 | 1.796 с | 0.496 с |
| 8 | 3.532 с | 0.562 с |

Во всех 18 измерениях подтверждены разные PID запрошенного числа workers и отсутствие живых workers после `close()`; [исходные значения](../validation/grain-shutdown/real-worker-measurements.json) сохранены отдельно. Локальное окружение использовало исходный Python-код и опубликованный native index-shuffle extension Grain 0.2.18. Это контролируемая задержка завершения, не throughput обучения. Скалярные результаты отделяют проверку lifecycle от другого дефекта владения shared memory, обсуждаемого в [#1420](https://github.com/google/grain/issues/1420) и [#1421](https://github.com/google/grain/pull/1421); мой PR не заявляет его исправление.

Полная нативная Bazel-матрица прошла для [финального head](https://github.com/jabrailkhalil/grain/actions/runs/38278915262) и [неизменённой базы](https://github.com/jabrailkhalil/grain/actions/runs/38272822537): Python 3.11/Linux x86, 3.12/macOS, 3.13/Windows, 3.14/Linux ARM. Это проверки в моём fork, не разрешение upstream CI. У базы первоначально завис отдельный macOS data-loader target; повтор только упавшего job на том же SHA прошёл. У head сначала была описанная выше собственная ошибка финализации, которую пришлось исправить до публикации PR. Эти два сбоя нельзя смешивать.

## Упражнения и границы применения

Добавьте третий ребёнок с исключением и проверьте, что очистка остальных всё равно завершилась до передачи ошибки вызывающему. Затем подмените `Thread.start` так, чтобы он отказал только для одного ребёнка: остальные должны завершиться, а отказавший — закрыться синхронно ровно один раз.

Наконец, придумайте пару cleanup-операций, которые нельзя распараллелить: например, обе зависят от определённого порядка освобождения общего ресурса. Барьерный тест доказывает перекрытие вызовов, но сам по себе не доказывает их независимость. Практический вывод — проверять и выигрыш, и сохранение lifecycle-контракта, включая путь ошибок и завершение интерпретатора.
